# 积分配置数据库设计

> 版本: v1.1  
> 更新时间: 2025-06-14  
> 状态: ✅ 已实现

## 一、设计目标

根据《小程序积分引流方案》，后台需要支持所有积分增减规则的可配置化，包括：
- 网站端基础积分（注册、登录）
- 小程序签到及连续签到加成
- 互动任务积分领取规则
- 创作激励配置
- 成就系统配置
- 激励视频广告配置（预留）

## 二、设计方案

### 2.1 复用现有 `system_config` 表

现有系统已使用 `system_config` 表（key-value 结构）存储积分配置，建议**扩展而非重建**，保持向后兼容性。

```sql
-- system_config 表结构（已存在）
CREATE TABLE IF NOT EXISTS system_config (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  description TEXT,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
)
```

### 2.2 需要新增的配置项

#### 基础积分配置

| key | 默认值 | 说明 |
|-----|-------|------|
| credits_register | 1 | 新用户注册积分 |
| credits_daily_login | 1 | 每日登录积分 |

#### 签到配置（小程序端）

| key | 默认值 | 说明 |
|-----|-------|------|
| credits_checkin_base | 1 | 签到基础积分 |
| credits_checkin_streak_3 | 1 | 连续签到3天加成 |
| credits_checkin_streak_7 | 2 | 连续签到7天加成 |
| credits_checkin_streak_14 | 3 | 连续签到14天加成 |
| credits_checkin_streak_30 | 5 | 连续签到30天加成 |

#### 互动任务积分领取规则

| key | 默认值 | 说明 |
|-----|-------|------|
| credits_claim_like_threshold | 10 | 点赞N次可领取 |
| credits_claim_like_reward | 1 | 点赞领取积分 |
| credits_claim_favorite_threshold | 5 | 收藏N次可领取 |
| credits_claim_favorite_reward | 1 | 收藏领取积分 |
| credits_claim_follow_threshold | 5 | 关注N次可领取 |
| credits_claim_follow_reward | 1 | 关注领取积分 |
| credits_claim_comment_threshold | 2 | 评论N次可领取 |
| credits_claim_comment_reward | 1 | 评论领取积分 |
| credits_claim_share_threshold | 2 | 分享N次可领取 |
| credits_claim_share_reward | 1 | 分享领取积分 |

#### 创作激励配置

| key | 默认值 | 说明 |
|-----|-------|------|
| credits_create_game | 2 | 创作游戏奖励积分 |
| credits_create_game_daily_limit | 1 | 创作游戏每日领取上限 |
| credits_edit_game_threshold | 2 | 编辑游戏N次可领取 |
| credits_edit_game_reward | 1 | 编辑游戏领取积分 |
| credits_edit_game_daily_limit | 1 | 编辑游戏每日领取上限 |

#### 激励视频广告配置（预留）

| key | 默认值 | 说明 |
|-----|-------|------|
| credits_ad_reward | 3 | 激励视频广告奖励 |
| credits_ad_daily_limit | 10 | 每日广告上限 |
| credits_ad_enabled | false | 广告功能是否启用 |

### 2.3 成就表配置

成就数据存储在 `achievements` 表中，后台允许修改以下字段：

| 字段 | 可配置 | 说明 |
|------|-------|------|
| reward_credits | ✅ | 奖励积分 |
| condition_value | ✅ | 达成条件值 |
| is_active | ✅ | 是否启用 |

**注意**：成就的 `condition_type` 和 `category` 不应该修改，因为涉及业务逻辑代码。

## 五、实现优势

1. **最小化数据库改动**：复用现有 `system_config` 表，只需添加新的配置项
2. **向后兼容**：现有配置项和逻辑不受影响
3. **统一配置入口**：复用 `getConfig()`/`setConfig()` 函数
4. **灵活可扩展**：后续新增配置只需添加新的 key
5. **成就动态化**：成就奖励和条件可后台调整
